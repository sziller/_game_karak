== Document purpose

This document is a state-transfer artifact for continuing the Karak multiplayer project in a new assistant instance.

Its purpose is to preserve:

* the architecture that has already been agreed,
* the implementation stages that have already been completed,
* the security and authorization boundaries that must not be weakened,
* the deployment and packaging decisions that have already been made,
* the current automated and manual validation baseline,
* the known limitations,
* the intentionally deferred work,
* the next recommended local proof-of-concept work,
* the questions that still need to be answered by the implementation assistant or by direct repository inspection.

The intended reader is a new AI assistant acting as architectural and coding manager for the project.

This is not intended to replace repository documentation, tests, or source inspection. It is a high-context handover that explains what the project is trying to achieve, why the current architecture looks the way it does, what is believed to be complete, and where the remaining uncertainty lies.

== Project identity and working relationship

=== Project

The project is a server-client, round-based implementation of the board game Karak.

The application currently uses:

* Python,
* FastAPI,
* server-rendered templates,
* vanilla JavaScript,
* an in-memory runtime registry,
* HTTP polling,
* package-based static and template resources.

The application is also designed to integrate into the wider SHMC framework, but standalone operation must remain possible.

=== User role

The user acts as architectural lead and product owner.

The user wants the assistant to act as a coding manager:

* define implementation stages,
* preserve architectural consistency,
* review implementation reports,
* detect scope drift,
* define acceptance conditions,
* avoid unnecessary code forks,
* avoid deployment-specific hard-coding,
* preserve future portability.

The coding assistant is expected to perform repository work. The architectural assistant should not pretend that code was inspected when only a report is available.

=== Preferred collaboration pattern

A new assistant should:

. First determine the current stage and accepted baseline.
. Avoid reopening completed architecture without evidence of a defect.
. Produce precise implementation prompts with explicit scope and non-scope.
. Require exact test commands and results in completion reports.
. Keep local, LAN, central-hosted, and packaging concerns separated.
. Preserve the same gameplay implementation across all deployment topologies.
. Treat manual physical-device validation as distinct from automated or same-machine browser testing.
. Prefer partial evidence and transparent limitations over confident assumptions.

== Product goals

The long-term product must support multiple use cases from one codebase and one package.

=== Hotseat

One human participant controls all player seats on one browser/device.

Hotseat is not a separate rules engine. It is a special ownership configuration within the common runtime architecture.

=== Central hosted Multiplayer

A centrally hosted server eventually allows multiple remote players to connect through the internet.

The central deployment is not yet the active target. Remote installation and public-host hardening are intentionally postponed until the local Multiplayer proof of concept is proven.

=== Player-hosted local Multiplayer

A user can run the game server on a local machine and allow other players to join.

Target host examples include:

* a personal PC,
* a family media center,
* a Raspberry Pi,
* another small Linux server,
* eventually a VPS.

Target client examples include:

* desktop browsers,
* independent browser profiles,
* family tablets,
* mobile browsers.

=== Multiple independently configured instances

The same installed package must support several independent server instances by changing configuration only.

Examples:

* one family instance,
* one test instance,
* several instances on a VPS,
* different ports,
* different advertised origins,
* different mount prefixes,
* different authentication integrations.

No source-code copy, branch-per-instance, or machine-specific code edit should be required.

== Non-negotiable architectural constraints

=== One gameplay implementation

There must not be separate Hotseat, LAN, and central-hosted game engines.

All topologies must use the same:

* game rules,
* `DungeonGraph`,
* `GameRuntime`,
* command authorization boundary,
* projections,
* revisions,
* polling,
* participant model,
* seat-ownership model.

Deployment topology may change configuration and transport exposure, but not game semantics.

=== `DungeonGraph` and `GameRuntime` remain separate

`DungeonGraph` owns game rules and game state.

`GameRuntime` owns session and server concerns around that graph, such as:

* runtime lifecycle,
* participant membership,
* host identity,
* seat ownership,
* participant credentials,
* revision,
* mutation locking,
* fault state,
* room-code lifecycle,
* safe state projection.

This separation is an `ARCHITECTURAL_DECISION`.

=== Process-local runtime registry

The current registry is in memory and process-local.

Conceptually:

[source,text]
----
game_id -> GameRuntime
----

Consequences:

* exactly one server process,
* exactly one worker,
* no multi-worker deployment,
* no horizontal scaling,
* no runtime persistence,
* all active games are lost on process restart,
* independent server processes have independent registries.

This limitation is currently accepted for local/LAN proof-of-concept and restricted staging.

=== Configuration-driven portability

The packaged implementation must not be specialized for one machine or environment.

Application code must not hard-code:

* a hostname,
* an IP address,
* a port,
* `/app/karak`,
* an SHMC repository path,
* a systemd unit,
* an Nginx location,
* a certificate path,
* a service user,
* a JWT issuer or audience,
* a specific Raspberry Pi or VPS setup.

Deployment-specific values belong in:

* package-safe defaults,
* selected instance configuration files,
* environment variables,
* explicit command-line overrides,
* operator-owned infrastructure files.

The intended precedence is:

[source,text]
----
package defaults
-> selected configuration file
-> process environment variables
-> explicit CLI overrides
----

== Core identity model

Three identities are deliberately distinct.

=== `game_id`

Identifies one `GameRuntime`.

It is not a participant or player identifier.

=== `participant_id`

Identifies one human membership in one game.

A participant may own one seat, several seats, or all seats.

Hotseat normally has one participant owning every seat.

Multiplayer normally has several participants owning different seats.

=== `player_id`

Identifies one game-engine or lobby player seat.

This belongs to the game state and seat model.

A participant acts for a player only when authoritative seat ownership grants control.

=== Why the distinction matters

The architecture must not collapse these identifiers.

The server must be able to answer separately:

* Which runtime is being addressed?
* Which human membership authenticated the request?
* Which game seat is being controlled?
* Does this participant own that seat?
* Does this participant hold the special decision role for the current pending state?

== Authentication and credential model

=== Application authentication

Application authentication proves that the browser/user may use the application.

Depending on topology, this may be:

* explicitly enabled local development authentication,
* standalone trusted-LAN authentication,
* SHMC browser authentication,
* central production JWT verification.

The packaged standalone game must not require SHMC.

=== Participant credential

The participant token proves membership in a particular game.

It is separate from the application bearer credential.

Header:

[source,text]
----
X-Karak-Participant-Token
----

The token is opaque.

Reported design:

* generated using `secrets`,
* SHA-256 digest stored,
* raw token returned once,
* raw token not stored in runtime state,
* revocable when participant leaves or game closes.

=== Expected revision

Gameplay and lobby mutations use an expected-revision credential/header.

Reported header:

[source,text]
----
X-Karak-Expected-Revision
----

This is concurrency control, not identity.

=== Credential separation invariant

A valid request may need both:

* application authentication,
* participant credential.

A room code is not a post-join credential.

A participant token must not replace application authentication.

Application authentication must not automatically grant ownership of a game seat.

=== URL secrecy

The following must never be placed in join URLs:

* application bearer tokens,
* participant tokens,
* participant digests,
* private pending-state data.

A join URL may contain the low-assurance room code.

== Runtime lifecycle and participation modes

=== Participation mode

Reported participation modes:

[source,text]
----
HOTSEAT
MULTIPLAYER
----

Participation mode determines participant/seat organization.

It must not create different rules-engine behavior.

=== Runtime lifecycle

Exact enum names should be verified in the repository, but the implemented flow includes at least:

* lobby/not started,
* in-game,
* closed or unavailable,
* fault handling.

The state endpoint dispatches projection according to lifecycle.

=== Room-code lifecycle

Room codes are used for Multiplayer admission.

Reported properties:

* human-friendly,
* generated with `secrets.choice`,
* reduced alphabet,
* six characters at the time of audit,
* invalidated after game start,
* invalidated after game close.

Room codes are low-assurance locators/admission secrets.

They do not authorize gameplay after joining.

Public-host rate limiting and brute-force protection are deferred.

== Locking, revisions, and mutation boundaries

=== Per-runtime lock

Each runtime uses a non-reentrant `threading.Lock`.

Mutation handling must avoid lock re-entry.

=== Revision

Every authoritative runtime mutation increments a monotonic revision.

The revision allows:

* polling change detection,
* stale-command detection,
* deterministic conflict handling,
* frontend projection ordering.

=== Common command boundary

Ordinary gameplay commands were migrated behind a shared server boundary.

Reported sequence:

. authenticate application user,
. authenticate participant token,
. resolve runtime,
. acquire runtime lock,
. validate lifecycle,
. validate expected revision,
. validate authority,
. call graph/game operation,
. increment revision exactly once on successful mutation,
. return sanitized result,
. release lock.

The boundary must not:

* retry stale mutations automatically,
* increment revision on denied commands,
* mutate before authority validation,
* grant debug authority to game host.

=== Conflict semantics

Reported behavior:

* `403` for authority denial,
* `409` for stale revision or relevant domain conflict,
* frontend performs one authoritative refresh,
* frontend does not retry the denied/stale command automatically,
* polling continues after recovery.

== State projection architecture

=== Unified state endpoint

The application moved from fragmented gameplay reads to one unified state projection.

Reported endpoint concept:

[source,text]
----
GET /api/games/{game_id}/state
----

Mounted prefixes may alter the browser-visible path.

The endpoint supports `since_revision`.

=== `204` behavior

When no state changed since the supplied revision:

[source,text]
----
HTTP 204 No Content
----

The frontend must:

* not render,
* not replace projection state,
* not change local revision,
* continue polling.

=== Projection requirements

The server projection must:

* be safe for the requesting participant,
* detach returned collections from live runtime state,
* avoid hidden pools and credentials,
* redact private pending decisions,
* expose participant-specific permissions,
* convert engine identifiers into frontend-compatible identifiers,
* avoid mutating the game while reading.

=== Read-side mutation problems previously found

A read audit found historical issues including:

* `/map` calling `ensure_entrance()` on GET,
* `DungeonGraph.serialize()` mutating compatibility position,
* `serialize_turn_actors()` lazily rebuilding,
* `Player.to_dict()` exposing Scout private pocket data,
* `TurnState.to_dict()` exposing live/private pending dictionaries,
* shallow live collections,
* engine numeric player IDs versus runtime seat IDs such as `p1`.

Stage 3B.1a introduced backend gameplay projection specifically to remove these risks from the active frontend path.

A new assistant should verify that no later refactor reintroduced fragmented or mutating reads.

Polling, manual refresh, and post-command refresh share a centralized synchronization controller.

* post-command synchronization uses the same coordinator.

The participant and game context are retained across reloads.

Exact storage keys and security behavior should be verified.

XSS exposure remains a future hardening concern.

== Authority model

=== Host authority

The game host controls lobby administration such as:

* creating/removing seats,
* assignment/unassignment,
* game start,
* game close,
* allowed administrative reset behavior.

Host authority must not imply:

* ownership of every Multiplayer seat,
* authority for another participant’s gameplay commands,
* debug authority,
* ownership of another role-specific pending decision.

=== Seat ownership

Ordinary gameplay authority follows seat ownership.

Examples:

* movement,
* tile interaction,
* ordinary inventory use,
* ordinary fights,
* skills,
* Scout actions where current rules permit,
* end turn.

A participant may act only for seats it owns.

Turn changes transfer effective command availability through the same authority boundary.

=== Special pending-decision authority

An audit found that active-seat ownership alone was not sufficient for all game situations.

The implementation added explicit authority policies for role-specific pending states.

Reported policies include:

[source,text]
----
PENDING_OWNER
CHALLENGER_OWNER
FIGHT_ROLE_OWNER
WINNER_OWNER
----

=== KO

KO decisions are owned by the affected player.

The authoritative pending state records an affected or owner player ID.

=== Arena challenge and fight roles

Arena behavior distinguishes:

* challenger,
* challenged participant,
* fight roles,
* winner,
* loser.

The challenged Arena participant may need to act even when it is not their normal active turn.

=== Arena loot

Arena loot authority belongs to the winner.

Loot selection must be validated against the pending stealable snapshot, not merely against current general inventory state.

Projection and UI must show controls only to the authorized participant.

=== Curse, poison, and healing

These pending decisions were given explicit `owner_player_id` fields and use the common pending-owner policy.

The architecture distinguishes:

* active player,
* target player,
* game host,
* decision owner.

A new assistant should preserve this distinction.

== Known limitations

=== No persistence

All games are lost when the process exits.

This is expected.

=== One process and one worker

Multiple workers would create multiple independent registries.

This is prohibited until shared state is designed.

=== No durable reconnect account

Reload restoration uses current browser/session storage.

A different browser or cleared storage is a different participant unless a future reconnect mechanism is added.

=== No public internet hardening

Current room-code and creation behavior are not ready for unrestricted public exposure.

Deferred controls include:

* rate limiting,
* room-code throttling,
* quotas,
* abuse prevention,
* token expiry,
* stronger browser session posture,
* public operational logging,
* persistence.

=== Package size

The package is large but functional.

This is deferred.

=== Physical-device UI

Tablet responsiveness, touch behavior, and older-device decoding performance remain to be measured.

=== Raspberry Pi performance

The wheel is pure Python and does not bundle x86-only binaries, but no real Raspberry Pi test has been performed.

=== Build reproducibility

Repeated builds were content-equivalent but not byte-identical because of archive timestamps.

This is not currently a blocker.
